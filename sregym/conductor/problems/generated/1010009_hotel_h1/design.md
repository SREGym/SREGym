# Durable profile batch contract regression

This evolves the previous cache-stampede suppression incident from a local mutex cycle into a persistent protocol failure. A distributed batch memoizer claims a normalized batch in MongoDB before loading ordinary hotel profiles. Its claim encoder hashes JSON arrays; the completion adapter hashes the compact display representation of the same sorted IDs. Producers return successful results and persist completed records, but readers never see those results under their claim keys. A second schema mismatch stores lease deadlines in epoch milliseconds and compares them with epoch seconds. Consequently, abandoned claims effectively never expire.

Existing user traffic deterministically creates claims; no artificial traffic, preseeded poison records, helper workloads, sleeps, or dependency denial is required. Most repeated batches then fail after an 800ms application deadline. Pods remain Running and Ready. The paired pending and completed records are real products of the application and explain why MongoDB connectivity and producer work can look healthy during the incident. This is a realistic cross-adapter identity and timestamp regression in a distributed request coalescer rollout.

The previous fixer's mutex repair does not apply: this implementation has no shared mutex. A restart retains database claims, and additional replicas encounter the same claims. Deleting records yields only transient recovery. Fixing the completion key leaves existing claims owned by retired processes until the lease reader is corrected or the claims are removed. ConfigMap source is compiled at startup; the database state supplies the second persistence boundary. The profile Deployment retains no retired revisions, matching a deployment-history pruning policy; recovery restores its original retention setting.

An expert follows profile lookup deadlines, establishes that ordinary cache/database work completes, then inspects `profile_batches` in `profile-db`. Pending records carry 13-digit numeric deadlines rather than BSON dates (there is no automatic TTL index), and completed records exist at different digest keys. Computing the two digests for a batch confirms the identity discrepancy. Correct the two contracts and clear obsolete pending claims, or revert to the image's ordinary `profile` entrypoint and drop this regenerable memoization collection. Hotel inventory is never modified.

`mitigate.sh` repairs the live code using only current cluster state and clears abandoned pending records. `recover.sh` restores the original Deployment specification and removes the regenerable collection and runtime ConfigMap. All scripts retire stale profile registrations after rollouts because the existing registry lacks health checks. Validation results are recorded separately in `validation.jsonl`.

Validation: two initial violated checks were separated by more than 60 seconds, including a restart. Mitigation ran twice and restored all four rounds to zero errors. Recovery ran twice, restored the exact original Deployment spec, and left all rounds healthy. The final script ran twice successfully; consecutive final checks again showed four violated rounds, approximately 99% errors, and large application log surges. Pending claims have no TTL index, and their millisecond values interpreted as seconds defer takeover for tens of thousands of years. No automatic recovery exists.
