# Cached codec prototypes cross the OpenResty request boundary

The previous incident was solved by reading `nginx.conf`, noticing the port-only pool key, and replacing it with hostname plus port. This incident retains correct endpoint identity and the stock `TSocket` implementation. It changes the abstraction being pooled: a plausible factory allocation optimization caches an endpoint protocol prototype and recursively copies its Lua object graph through a separate cache helper.

The helper copies tables recursively and preserves class metatables, but returns non-table values unchanged. A cosocket contains internal resource userdata; the copied graph retains that request-owned resource. Returning its TCP connection with `setkeepalive` does not make that userdata valid in another request. Reopening it in a later request fails with `bad request` in `TSocket:open`. This is an object-lifetime defect, not a destination collision, semaphore leak, admission limit, or traffic-capacity problem. Worker count and resource settings remain at their original defaults.

The factory and cache helper are registered through `package.preload` in the existing frontend ConfigMap's startup Lua. All application images, volume mounts, Services and endpoints remain unchanged. No auxiliary workloads or controllers are added. Restarting creates successful cold calls followed by sustained errors. Deployment rollback retains the ConfigMap startup code.


An expert examines logs and traces to establish that requests fail before backend RPC spans, checks successful direct backend connectivity, and follows the factory's new object construction. Recursively copied tables, preserved class metatables and empty frame buffers initially look safe. Following the non-table leaf values into the cosocket implementation and comparing them with OpenResty's request ownership rules identifies the retained resource. Allocate a fresh TSocket per HTTP request, allowing only the underlying TCP connection to be pooled. The reference scripts remove the startup registration to restore the installed factory using cluster state alone. No original files or secret values are required.

`mitigate.sh` restores the original nginx configuration and restarts workers; `recover.sh` also removes the restart annotation to restore the original pod template. Injection and cleanup are idempotent. Validation files record full 120-second SLO windows; early exploratory files are removed before delivery. Acceptance evidence covers repeated injection, persistent failure after restart, full healthy windows after mitigation and cleanup, and final replay.

Final validation: all three scripts ran twice successfully. Two checks more than 60 seconds apart confirmed the startup-code incident; Deployment rollback retained the violation. Mitigation and recovery each passed all 11 rounds with zero errors in complete 120-second windows. Final replay again violated all 11 rounds in both checks with a large frontend log surge. The incident has no expiry or reconciliation mechanism; cached request-owned resources remain invalid until the factory is corrected. The cluster is left with the incident active.
