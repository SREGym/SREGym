# Distributed RPC capacity reservation leak

A rollout adds a Redis-backed concurrency guard to nginx's existing Thrift pool through `init_by_lua_block` in the existing `nginx-thrift` ConfigMap. The guard admits 64 simultaneous calls per upstream. Each reservation has a one-hour orphan reclamation period. A shared ledger is appropriate when multiple frontend replicas must protect a small backend; long reclamation is a plausible conservative policy when avoiding duplicate admission is prioritized.

The release path expects `transport:setKeepAlive(...)` to return successful socket ownership transfer. The deployed `TSocketBase:setKeepAlive` wrapper invokes the underlying OpenResty API but returns nothing. Every successful call therefore leaves its reservation behind. At production traffic rates each upstream's ledger fills within seconds. Ordinary health checks continue to pass, Redis accepts commands, and backend services remain available. Capacity is stranded rather than consumed by actual RPC work. The one-hour retention exceeds the required 30-minute interval; steady traffic refills permits immediately as old reservations expire.

The controller lives in the ConfigMap, not the Deployment revision. Restarting or rolling back the frontend reads the same code, and the Redis ledger outlives all frontend pods. Scaling adds callers against the same budget. Removing keys without repairing the release contract gives only a short recovery. The incident is distinct from connection identity collisions and lock inversion: destination keys are correct and no mutex cycle exists; successful completion does not return capacity.

An expert follows frontend queue errors to the effective startup Lua, checks `ZCARD` and reservation timestamps in `rpc:admission:*`, and compares occupancy with actual RPC activity. Reading `GenericObjectPool` and the deployed `TSocket.lua` exposes the mismatched return contract. Disable the newly introduced guard, or fix permit release for completion and failure and retire stale leases. `mitigate.sh` implements disabling it using the cluster's existing ConfigMap and the pool already shipped in the container image. Redis deletion is restricted to this obsolete ledger; graph and user data are untouched.

`inject.sh` is deterministic and idempotent: it replaces just the admission block, patches the ConfigMap and restarts nginx only when configuration changes. There are no helper resources or timing sleeps. `mitigate.sh` is idempotent. `recover.sh` additionally removes the rollout restart annotation, restoring the original pod template and ConfigMap contents. Deployment controller revision counters and historical events naturally remain Kubernetes audit history.

Validation evidence is recorded in accompanying JSON files. The original healthy workload sustained approximately 100 requests/sec with zero errors. Two checks more than 60 seconds apart showed SLO violations, with the latter reporting 11/11 violating rounds and 100% errors; nginx error logs surged by over 20,000 lines. Frontend restart and rollback to the original pod template preserved the incident. Mitigation and cleanup each passed all 11 rounds in complete two-minute windows; both scripts were executed twice successfully. Cleanup restored the original Deployment spec and ConfigMap contents exactly. Final replay checks are recorded separately.

Final replay: two complete 120-second windows, checked more than 60 seconds apart, each reported 11/11 violating rounds with error ratio 1.0 in every round and over 20,000 new nginx error lines. The incident was left active for submission.
