A supplier import retention companion was enabled for the profile datastore. Its policy correctly names the dotted MongoDB collection `staging.hotels`, but a qualified-name parser copied from table-name handling strips every prefix and selects `hotels`. In MongoDB, the database is already supplied separately and the dot is part of the collection name. Legacy supplier rows 2–6 have no `importedAt`; the import compatibility default is the Unix epoch. A one-day retention rule therefore immediately expires those five rows. The controller archives the first full revision in `hotel_catalog_versions`, stamps `_retention.expiresAt`, maintains a native TTL index, and sweeps expired records every ten seconds. Its normal expiry invalidation also deletes the corresponding profile cache keys, including republished keys whose source row is still retired. The explicit initial reconciliation makes reproduction independent of the native TTL monitor tick.

This mirrors a staging retention rollout applied to live business data. Qualified-name normalization and missing timestamp semantics cause the loss; neither infrastructure failure nor inaccessible credentials are involved. The companion is a permanent application maintenance container, not a leftover administrative helper. Its ConfigMap, source, logs, archived revisions, and MongoDB index are visible using kubectl. It does not access the Kubernetes API or any other namespace.

There are two amplifiers already present in the application: profile logs a missing row but still returns a successful empty profile, and caches that profile forever; frontend dereferences its absent address during GeoJSON serialization. net/http recovers the panic and closes that request's connection. Consequently the frontend keeps running, traces often show successful dependency calls, many routes and catalog keys work, and the first visible runtime error points at response formatting. Between expiry invalidations, negative entries hide repeated MongoDB reads even though user errors continue. The expiry invalidator defeats repairs that only warm a positive cache over still-missing source rows. Restarts do not remove the independent cache. Regenerating database rows does not defeat periodic retention, and dropping its index does not stop explicit sweeps.

An expert correlates failing routes or requests with profile IDs, reads raw cache values for affected IDs, compares them with MongoDB live records and archived revisions, then examines index management, the companion's mounted policy, and its collection-name parser. The policy itself looks correctly scoped to staging; the implementation contradicts it. The complete repair changes the controller to preserve the full collection name first, restores catalog revisions, and only then clears the profile cache. `mitigate.sh` uses those discoverable cluster objects and no saved state. `recover.sh` restores the original Deployment spec, documents, and indexes and removes new maintenance objects/collections. Original snapshots are captured only once for cleanup and are not exposed in Kubernetes.

Scripts use the existing MongoDB and Python interpreters through kubectl exec. There are no temporary pods or jobs, no observability changes, no host changes, and no external workload interactions. The readiness probe waits for actual database availability; injection performs an explicit reconciliation after rollout instead of sleeping for a startup or TTL race. The timer inside the permanent companion is its normal reconciliation cadence.

Live validation: the baseline had four healthy rounds, about 97 requests/s and zero errors. Two violation checks more than 60 seconds apart both had four violating rounds; error ratios were approximately 14–16% and p99 was 12.8–15 seconds. Frontend error-like logs rose from zero to approximately 4,000 lines per two minutes, while application pods remained Running and Ready. A partial repair restored 80 rows and removed the TTL index; within a reconciliation cycle the controller returned the live collection to 75 rows and recreated the index. Full mitigation was executed twice and yielded four healthy rounds, zero errors, and p99 43–69 ms. Cleanup was executed twice, then the original Deployment spec, all original document values/ObjectIds, and original indexes were compared and found identical; its subsequent four-round SLO window was healthy. Injection is then repeated on that clean state for the final active incident. The controller has no end time or expiry of its own and continuously removes regenerated live rows and invalidates their cache keys; no natural healing path exists.

Cleanup snapshots are keyed by the immutable MongoDB Deployment UID. Thus a writable artifact copy replayed on a fresh Deployment captures its own original state even if it contains validation snapshots from this session.

Final replay on the exactly restored baseline also succeeded twice consecutively. Two final checks, more than 60 seconds apart, each showed 4/4 violating rounds, approximately 13–16% errors, p99 about 12–15 seconds, and 3,827–3,975 frontend error-like lines per two minutes. All application pods were Running and Ready. The incident was left active for submission.
