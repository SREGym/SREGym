# Historical catalog materialization scope regression

A catalog migration publishes a compatibility export over current inventory and an archival tariff partition. A recurring catalog refresh process materializes this export into the legacy application's physical `inventory` collection. Its source view accidentally uses an unrestricted union, so history is repeatedly imported into current inventory. The rate service filters only by hotel ID despite accepting arrival/departure dates, exposing a latent query assumption.

The archive has 256 nightly advance-purchase tariffs for each of 80 hotels, all dated in 2014. Each contains ordinary 3.5 KB booking conditions; the largest BSON document is only 3,719 bytes. Original current documents, IDs and indexes are preserved. One hotel's derived cache value is about 947 KB, below the default 1 MiB item limit, but five hotels aggregate beyond the default 4 MiB gRPC receive budget. Serialization and sorting also increase rate CPU and produce deadlines.

This evolves the parent's persistent catalog/cache amplification family. The former decisive image-description search finds nothing. Deleting records from the served collection and flushing cache can temporarily help but the materializer restores historical rows from the source archive. Source-only repair leaves non-expiring cache values. No restart or application deployment rollback fixes the source data projection. There is one causal chain: archive scope, repeated materialization, unbounded legacy query, cached aggregate amplification.

The materializer is a normal application data-maintenance sidecar, using the existing MongoDB image, mounted `catalog-refresh` script and live MongoDB credentials. It runs every 30 seconds and logs successful refresh output or connection errors. It is part of the incident, not a diagnostic helper; replay creates no helper Pod or Job. Capacity tuning gives rate eight CPU cores, a long cache timeout, one search attempt, and a 128 MiB cache. Replay drains workers and warms all cache keys from live inventory before restoring replicas. This avoids the legacy cache-builder's repeated-concatenation cold-start pressure dominating the incident. The replay script does not sleep to wait on races; its waits use rollout and pod deletion conditions. The only sleep belongs to the recurring production refresh loop.

An expert follows search dependency failures to rate. Aggregate counts by hotel, code and dates rather than only sorting BSON sizes. Compare archived dates with live request dates, and read services/rate/server.go to establish that Find filters only hotelId. Inspect database collection/view metadata: `catalog_export` unions `inventory_current` and `inventory_history`. The Mongo deployment's refresh sidecar and its mounted script show how these rows reappear in inventory. Inspect a cache item's size and the application's zero-expiration Set calls to identify the independent derived copy.

The reference repair narrows the export to its current backing collection, drains the materializer by removing its sidecar, rebuilds inventory from the preserved live catalog, drains old rate workers and flushes their shared cache. It uses only live cluster objects, database metadata and the application's established credentials; no private snapshots are required. Recovery additionally drops introduced archive/export/current-copy objects, deletes the refresh ConfigMap and restores modified deployment settings from their existing last-applied annotations. Existing application data remains unchanged.

The scripts use deterministic per-hotel/date upserts and are idempotent. Validation captures SLO response JSON for the successful final replay and recovery cycle.
