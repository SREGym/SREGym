# Supplier revision cardinality migration

A supplier catalog migration retains a representation that supports multiple identifiers and addresses in the existing live collection. Five popular hotels have both this representation and their unchanged canonical scalar records. The existing nonunique id index is now multikey. An unqualified lookup by legacy scalar ID selects the retained array representation. The legacy Go protobuf model accepts only a scalar ID and an address object; mgo silently leaves those incompatible fields empty. The profile RPC succeeds and caches the incomplete value without expiration. Frontend serialization dereferences the absent address.

This is one coherent partial schema migration incident, rather than a collection of unrelated disruptions. No deployment, configuration, auxiliary collection, index, controller, or helper pod is added. All original documents and ObjectIds remain available. Both representations contain full address enrichment. The retained supplier alias follows a normal supplier identifier format.

The previous solver located address-less retired rows, grouped duplicate IDs, removed those rows, and flushed the cache. Here there are no address-less rows or lifecycle markers, and that aggregation returns no duplicates: MongoDB groups the array and scalar identity values separately, yet equality lookup and uniqueness constraints overlap them. A unique index build fails instead of preventing the incident. Restart and cache flush reproduce it. This requires inspecting actual BSON cardinality rather than merely presence, and explaining why a complete MongoDB address becomes null in cached JSON. Fixer difficulty is a hypothesis pending independent solver evaluation.

An expert follows frontend panics through successful profile spans, inspects the cached hotel, compares all rows returned by an equality lookup with exact scalar-type records, and checks the protobuf/BSON reader contract. The reference mitigation removes incompatible retained revisions only after verifying a canonical scalar counterpart, then clears the durable cache effect. Recovery restores a deployment-UID-scoped snapshot of exact original documents. The script snapshots are solely for cleanup; mitigation uses only live cluster data.

Injection verifies lookup selection explicitly and contains no timing races or sleeps. Existing array revisions are replaced, making replay idempotent. MongoDB state has no expiry and persists across application restarts. Validation results follow below.

Live validation: baseline was 4/4 healthy rounds with zero errors. Injection, mitigation, and recovery each ran twice consecutively with exit 0. A profile restart and profile-cache flush left the incident active. Initial violation checks more than 60 seconds apart passed, with frontend log surges of 3,850–4,087 lines per two minutes. Mitigation produced 4/4 healthy rounds, p99 59–78 ms. Recovery matched the original serialized catalog byte-for-byte and produced 4/4 healthy rounds with zero errors, p99 78–86 ms. Final replay ran twice; two checks more than 60 seconds apart each showed 4/4 violating rounds. Final errors were [0.1473, 0.1414, 0.1342, 0.1433]; final p99 milliseconds were [15520.0, 13740.0, 14300.0, 13560.0]. Frontend log surge was {'hotel-reserv-frontend': [0.0, 3890.0]}. All application pods remained Running and Ready. There is no expiry or healing mechanism. Raw validation responses are included in the artifact directory.
