# Numeric widening and native lease attrition

A storage maintenance migration widens the existing `post.post.media[].media_id` values from BSON int64 to Decimal128 without changing any numeric identifier. At the same rollout, the post-storage client's MongoDB pool is bounded to 16 clients, a plausible connection-budget tuning. Neither the gateway nor its Lua configuration changes. No resource, collection, field, controller, or auxiliary process is added.

The native post reader serializes BSON through JSON. Decimal128 becomes an extended-JSON object instead of the numeric representation expected by the media decoder. A timeline read therefore raises a numeric type exception while owning a MongoDB client. The exceptional path fails to return the client to its pool. A few failed reads exhaust the pool, after which MongoDB checkout blocks normal post writes as well. The steady-state symptom is compose RPC read timeouts and very low throughput, far from the original media decode failure. MongoDB remains healthy and has ample global connection capacity; all application pods remain Ready.

This evolves the parent's lease migration family by exploiting the application's native pool ownership rather than installing an admission controller. The earlier successful removal of gateway startup adapters has no target here: nginx ConfigMap, image modules, and Deployment remain unchanged. The state is in an existing document's nested numeric representation. Pool size is a pre-existing setting with an ordinary positive value. The early exception is small relative to total traffic; lease attrition turns it into a broad persistent capacity failure.

An expert correlates early timeline numeric type exceptions with subsequent compose timeouts, notices that post storage is idle despite pending RPCs, and compares its configured pool size with MongoDB connections. A BSON type audit of nested media IDs identifies Decimal128 values; a normal top-level document check may miss this distinction. Compare `$type` and the driver's extended-JSON representation, rather than merely comparing numeric values. Existing exporter DNS errors predate the incident and are unrelated.

Restarting post storage or clearing post cache replays the same data and consumes capacity again. Increasing the pool only increases the number of decoding failures tolerated. Fixing stored identifiers does not return already stranded clients in a live process. The reference repair converts Decimal128 media IDs back to exact signed 64-bit integers, restores the known application pool default of 512, flushes the regenerable post cache, and replaces only post storage. It uses live state and well-known defaults. Recovery additionally restores the exact saved ConfigMap bytes; snapshots are keyed by ConfigMap UID so fresh replays capture their own state.

Injection is a bounded MongoDB migration and a ConfigMap value edit. It replaces the affected process only when the effective configuration changes, then retires cached encodings. No sleep, race-dependent trigger, helper workload, or permanent helper resource is needed. Ordinary application traffic deterministically exercises the migrated records and strands the bounded pool. The incompatible data outlives application restarts, and checked-out clients do not expire or spontaneously return. Numeric conversion is exact and reversible; no user content or unique identifier value is discarded.

## Validation

Live checks are recorded under `validation/`. The first sustained injection produced two violating checks 85.7 seconds apart, each with 11/11 violating rounds. Replacing post storage without repairing data reproduced the collapse. Repairing data without replacing the process left all three recent rounds violating at 0.8–1.8 requests/sec.

Mitigation and recovery each ran twice with successful exits. Their two-minute checks showed 11/11 healthy rounds at approximately 102 requests/sec. The original ConfigMap data matched exactly. An additional replay migrated 9,549 posts, and the full mitigation script converted all 9,549 back. Its cleanup check again showed 11/11 healthy rounds, no remaining Decimal128 media IDs, and four MongoDB connections versus eighteen during saturation.

Final injection ran twice successfully, preserving the replacement pod on its second run. Both final two-minute checks violated; they were separated by 161.0 seconds. The latter reported 11/11 violating rounds and a gateway log surge of [0.0, 80.0]. All final application pods remained Ready. The incident is left active.
