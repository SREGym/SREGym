This incident models an operator's content backup utility left running in an existing media database container. The utility discovers Redis's `config_file` through `INFO server` and incorrectly treats that path as the RDB output path. It consequently sets the existing runtime `dir` and `dbfilename` settings to the directory and filename of the mounted Redis configuration, reapplies the normal snapshot policy and `stop-writes-on-bgsave-error yes`, and requests a background save every 300 seconds.

Redis runs as its normal unprivileged user. The configuration directory is not writable, and the selected final filename is a mounted ConfigMap file. The failed background save activates Redis's normal write protection. User timeline cache writes and post publication fail, including timeline reads that need cache population. Kubernetes manifests and readiness remain healthy. Redis logs show real persistence errors; the timeline RPC service and nginx emit real MISCONF-related errors. The initial live measurement showed roughly 40% errors.

The recurring source is a normal detached bash maintenance process in `media-mongodb`, not a Kubernetes object. It resolves the Redis Service name anew on each pass, so replacing Redis or the failing RPC service does not remove it. Correcting runtime settings or disabling write protection gives temporary recovery, but the next pass reverses the repair. No application data is deleted or modified by the utility; snapshots to the mounted configuration path cannot overwrite that file.

An expert would follow timeline errors to Redis, compare `CONFIG GET dir`, `CONFIG GET dbfilename`, `CONFIG GET save`, and `INFO persistence` with the Pod's actual startup configuration, and repair the snapshot destination. The return of the runtime changes despite an unchanged ConfigMap establishes an external writer. Redis `CLIENT LIST` identifies the idle maintenance connection, whose last command becomes `bgsave` after a pass; mapping its address to a Pod and inspecting `ps` and `/var/tmp/content-snapshot.sh` finds the orphaned utility. Stop it before restoring the snapshot destination, and verify a successful save plus healthy traffic for longer than one cadence.

`inject.sh` captures only the four original runtime settings under `$ARTIFACT_DIR/state`, installs the process inside the existing container, requests the first save synchronously through its utility, and polls the explicit background-save status before returning. Its sleeps are the operational process's recurrence interval, not startup synchronization or race-based injection. Repeated invocation preserves the original settings and reuses the same process. The saved settings are associated with the Deployment UID, so a fresh deployment gets its own baseline. `mitigate.sh` uses only live process state and the standard Redis image defaults. `recover.sh` additionally restores the captured settings exactly. Neither script changes the observability stack, workload generator, system components, or application manifests.

Live validation completed: repeated injection produced two fully violated SLO checks more than 60 seconds apart; repeated mitigation and recovery each returned every measured round to health. A one-time Redis destination repair recovered requests and then regressed on the maintenance pass. The final active run remained violated for at least 30 minutes, with every post-warmup measurement round failing and continuous nginx/timeline error-log surges. All application pods stayed Running and Ready.
