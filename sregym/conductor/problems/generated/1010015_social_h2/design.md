# Endpoint microbatching loses RPC ownership

An RPC optimization introduces endpoint dispatch lanes that coalesce complete framed messages for 250 ms. Each fresh client still receives a fresh protocol, framed transport and TCP socket; host-and-port identity is correct. The transport adapter queues frame header and payload bytes together and forwards other socket operations through a view of the endpoint lane.

The defect is ownership. Every new call rebinds `lane.transport`. When a coalescing window ends, pending frames from multiple calls are written to the latest socket. Independent clients subsequently resolve that same mutable socket for reads, close and keepalive return. There is no exclusive checkout and no reply demultiplexer. An earlier call can read or close another request's socket, while its own socket receives no request. Full frames remain correctly encoded, so this is a concurrent channel ownership regression rather than a wire-format change or a wrong pool key. The same allocation-tuning rollout consolidates nginx to one worker. Resource settings and backend configuration remain unchanged.

The 250 ms window is a plausible small-message batching setting. It is below the one-second SLO limit and a sequential timeline probe completes successfully in about 260 ms. The batching setting also reduces effective synchronous request capacity: the observed workload drops to roughly 8–12 requests/sec even with automatic workers. One worker makes ownership overlaps more frequent. With live concurrent traffic, invalid socket ownership, competing reads and missing replies cause HTTP failures and long tails. Removing only the batching delay leaves the unsafe late-bound transport view: the no-delay, one-worker variant produced 11/11 violating rounds with approximately 12–18% errors. Restoring automatic workers alone retains the batching throughput collapse. These are coherent contributing defects in one allocation and dispatch optimization.

The parent's five-minute repair removed a clearly delimited preload block in `nginx.conf`. There is no such block here. The original factory and socket implementation remain intact. The modified framed-transport module and registry are ordinary source keys in the existing frontend ConfigMap, mounted over installed modules using subPath mounts. Image rollback and pod recreation retain those sources. No auxiliary workload, external controller or observability changes are involved.

An expert starts with failed read/close stacks and successful backend RPCs, observes the difference between sequential and concurrent requests, inspects module mount provenance, and follows `TFramedTransport:new` into the registry. The endpoint key and frame boundaries are correct. The mutable lane instead combines several request identities on one request-owned transport. Repair must restore per-call socket ownership and remove the shared frame queue, or implement a true multiplexing channel with request/reply correlation. Removing the adapter restores the installed per-request implementation and normal connection keepalive behavior.

`inject.sh` embeds both complete module sources and deterministically deploys their ConfigMap keys and mounts. Repeated injection recreates workers so subPath sources refresh. `mitigate.sh` derives its fix from live cluster state and restores the normal automatic worker setting. `recover.sh` restores the saved original ConfigMap data and pod template exactly; saved state is local and never deployed. All scripts are idempotent. A fresh ConfigMap UID causes fresh recovery state to be captured.

Final validation: both initial incident windows and both final replay windows violated all 11 rounds, with a reported nginx-thrift log surge. Checks in each pair were separated by at least 60 seconds. Mitigation and recovery each passed all 11 rounds with zero errors. Each script ran twice successfully. Recovery restored original ConfigMap data and the deployment pod template exactly. Final replay remained violated after Deployment rollback; module mounts, source and the worker setting were retained. The incident has no expiry or self-healing path. Full SLO responses are retained in `validation/`.
