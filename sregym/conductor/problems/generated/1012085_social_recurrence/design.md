The incident is a leftover cache-policy publisher launched during a durability-policy rollout. An operator ran it in the existing relationship database container because the social graph is the source of timeline audience state. Its policy was copied from a replicated, durable store: one acknowledged replica is required before writes. Both timeline Redis instances in this deployment are standalone ephemeral caches, so the policy prevents writes while leaving their primary roles, TCP listeners, reads, and Kubernetes readiness intact.

The publisher immediately applies the setting and then waits six minutes between refreshes. It uses Service DNS and reconnects each time, so restarting either cache, rolling back its Deployment, or changing its runtime setting does not retire the publisher. The six-minute idle period allows a repaired cache to pass a full two-minute SLO observation before the next refresh regresses it. There are no new Kubernetes objects, collections, configuration keys, RBAC changes, or startup modifications. One existing configuration value changes in each of two caches. This differs from a standby reconciler: Redis never changes replication role or upstream; the failure is an independently enforced write-quorum admission policy.

An expert follows frontend posting/cold-read errors into UserTimelineService, checks Redis INFO replication against CONFIG GET min-replicas-to-write, and recognizes that a standalone master cannot satisfy the policy. Because an unexplained runtime value may have an external writer, the expert keeps Redis MONITOR running across a refresh. It exposes the CONFIG SET client address, which maps to the unchanged social-graph-mongodb pod. Inspecting /proc or the process tree there reveals the unmanaged cache-policy-sync shell process and its sleep child. Stop that process before restoring both standalone-cache defaults, then watch beyond one refresh interval. The existing MongoDB data and Redis timeline contents remain intact.

inject.sh saves only the original two Redis runtime values in the artifact directory for exact cleanup, performs a synchronous first publication, and starts at most one detached publisher per source container. Subsequent calls republish without creating additional workers. The periodic wait implements the operational refresh interval; it is not a startup race or a delay used to make injection succeed. mitigate.sh needs only live cluster state and the application default. recover.sh also restores the recorded runtime values and removes the publisher files.

redis-config.sh is a shared Bash helper that issues CONFIG GET/SET over Redis's native RESP protocol. All artifact scripts use only kubectl, Bash, coreutils, and Python 3; no database client, additional package, or external application access is required. Preserve this helper alongside the three entry-point scripts when copying the artifact directory.
