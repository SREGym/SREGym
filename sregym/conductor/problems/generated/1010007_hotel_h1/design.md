# Blocking-query discovery cache collision

A Consul API caching facade was added for the high-read geographic and pricing discovery paths. It forwards writes, catalog reads, and ordinary health reads to the native Consul agent. A cache-key refactor scopes blocking-query responses to the collection path (`/v1/health/service`) instead of the complete service resource. Its normal geo warmup snapshot consequently satisfies both geo and rate watches. Cached responses have no invalidation tied to catalog writes. This combines two common API-cache mistakes: dropping a resource identifier during key normalization and retaining an index-bearing response without maintaining its watch semantics.

Search initially receives a correct rate snapshot. Eight seconds later, its next Consul blocking query replaces the rate address with the healthy geo gRPC address. Geo accepts the transport but cannot implement the Rate method. Search emits its normal `dependency=rate grpc_code=Unimplemented` warnings and returns a generic unavailable response. No application binary, rate configuration, credential, or authoritative registration is wrong.

The earlier fixer used a catalog listing to spot a cross-service orphan and deregister it. Here that listing contains only valid rate registrations. `health/service/srv-rate?passing=true` also returns the real rate server. Running wget inside the native Consul container bypasses the facade and therefore returns correct results even for indexed requests. Re-registration and catalog deletion cannot clear the already cached snapshot. Restarting or rolling back search initially looks promising, then the next resolver watch restores the incorrect route. A Consul deployment rollback alone removes the facade listener while its Service still routes to that listener, so it is not a complete repair.

An expert reads the resolver source available in the application image, reproduces its `index` and `passing` query parameters through the Consul Service, and compares the response with the native agent. A correct ordinary response and an incorrect indexed response localize the issue to the facade rather than to registration ownership or gRPC implementation. Inspecting `consul-query-cache` then reveals the missing service segment in `cache_key`. A permanent code repair preserves the complete resource path and correct blocking-query invalidation. The emergency mitigation bypasses the cache through the existing Service and refreshes search connections.

The incident persists indefinitely while the facade remains enabled. Warmup is synchronous and deterministic, and does not require a race between service registrations or queries. All created cluster artifacts are normal application infrastructure: a cache sidecar and its mounted source ConfigMap. There are no helper pods, jobs, agents, synthetic log messages, or observability changes. Deployment replacement preserves legitimate agent registrations across the dev-mode Consul restart. Recovery and replay refresh frontend connections after an index reset so obsolete blocking watches cannot affect the settled validation window. Search rollout cleanup removes registrations whose addresses no longer belong to live search pods. Recovery restores the saved original pod templates and Service ports and removes the cache ConfigMap. The snapshot is keyed by deployment UID, so replay on a fresh cluster captures its own baseline. Mitigation uses only live cluster state and the standard native Consul port.

## Live validation

The initial settled incident produced approximately 59–61% end-user errors. Two SLO checks more than 60 seconds apart reported `violated=true`, with every measured round violating. Search error logs rose from zero to more than 6,800 lines in the comparison window. A search deployment rollback did not restore service. Ordinary catalog and health responses remained correct while an indexed rate health query returned the geo registration.

The final mitigation script ran twice successfully. Its full four-round window was healthy. Recovery ran twice successfully after adding explicit frontend connection refresh for the dev-mode registry index reset. Original Consul and search templates and Consul Service ports were compared with the captured baseline and matched exactly; the added ConfigMap was absent. Four settled recovery rounds had zero errors.

The final injection script was then run twice from the recovered baseline. Final settled replay results are appended after verification.

Final replay: both checks more than 60 seconds apart reported `violated=true`, with all four rounds violating. Settled end-user error ratios were approximately 58–61%, and search error-like logs exceeded 6,700 lines per comparison window. Every application pod remained Running and Ready. The incident is left active for submission.
