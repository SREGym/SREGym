# Static HTTP/2 window and connection-credit batching regression

A search transport tuning rollout fixes the receive windows of the rate-client connection at 64 KiB, replacing adaptive BDP window growth. The same rollout refactors the vendored gRPC flow controller to support an optional per-connection batching threshold; streams and servers retain their default quarter-window threshold. The static-window override accidentally assigns `uint32(icwz)*4` rather than `uint32(icwz)/4`. The adaptive connection retains its normal quarter-window default.

This is a ratio/unit error in a network transport optimization. The peer can send at most one window of DATA without receiving credit, but the client will not flush its accumulated credit until four windows have been consumed. The peer therefore runs out of credit before the client can reach the update threshold. Small RPCs finish initially because each fresh stream has its own full stream window. Their shared connection window steadily drains. The other adaptive client connection retains the normal threshold; only the manually tuned rate path uses the erroneous override.

Search and rate stay Running and Ready. Consul addresses, Service ports, TCP handshakes, HTTP/2 HEADERS and PING, and backend queries are healthy. The rate server can finish application work but cannot deliver DATA for the completed RPC. Search deadlines and retries continue to run, producing its existing dependency=rate / DeadlineExceeded warnings and timeout metrics. The frontend logs failed searches; recommendations, user, and booking connections remain untouched.

The runtime consists of three ordinary Go source files in a shared `search-runtime` ConfigMap, mounted over the corresponding source already shipped in the application image. The search entrypoint builds the shipped command with the vendored runtime. A TCP readiness probe ensures the build has reached its listener before rollout completes. Injection first establishes the healthy static-window refactor, then changes the static-window override ratio in the same shared ConfigMap. Both Deployment revisions reference that object, so an ordinary undo of the latest Deployment does not undo the source contents. Restart and scale-out each restore only a finite connection-credit budget. The source configuration has no expiry or self-repair mechanism; canceling an individual RPC does not reset its healthy TCP connection, so the bad credit state persists until a connection is replaced and promptly recurs on the replacement.

An expert would compare increasing search timeouts with completed rate spans and low rate queue depth. A fresh client succeeding briefly while the long-lived search connection fails suggests connection state rather than endpoint health. HTTP/2 frame inspection shows missing connection WINDOW_UPDATEs with continuing control frames. Compare the mounted client static-window branch and flow controller against the source shipped in the original image; the threshold must fit inside the advertised receive window. The reference repair edits that one live ConfigMap expression and restarts search. It uses only cluster state.

The scripts also remove retired search registrations during their normal rollouts because the stock application registers endpoints without TTLs. This prevents stale pod-address entries from becoming a second incident. Cleanup restores the original search pod template and removes the runtime ConfigMap. Application data, other workloads, and all observability resources are untouched.

Measured validation and persistence checks are in validation.jsonl. Replay solver success rates cannot be known before submission.
