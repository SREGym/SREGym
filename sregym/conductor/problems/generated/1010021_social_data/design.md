This incident models a timeline-store migration that imported two million empty historical account timelines and optimized index size by retaining only nonempty timelines in `user_id_1`. Historical records use the existing collection and its ordinary `user_id`/`posts` schema. Live timelines are restored after the archive, preserving their contents. No application configuration, code, network paths, or telemetry components are altered.

The subtle error is query implication: the application uses `findAndModify` with only `user_id`, while the unique index has `partialFilterExpression: {"posts.0": {$exists: true}}`. Even though active users have posts and are present in the index, the optimizer cannot prove the query excludes empty timelines. Each synchronous write therefore scans the historical rows before reaching the live record. Composition waits for this operation. Redis is only a read acceleration layer; clearing it does not repair the write access path.

The stock deployment has ephemeral MongoDB storage. The script migrates the timeline database onto a conventional, namespace-local PVC before importing the history. It temporarily pauses timeline writers for a consistent copy, then restores the original replica count. This is necessary to preserve data and the index through a database pod restart; the storage object contains no repair recipe or diagnostic hints. No helper pods remain. The reference repair preserves all data and storage.

An expert would correlate compose latency with timeline spans and MongoDB CPU, inspect slow-operation `planSummary`/`docsExamined`, and explain the exact user-only predicate. `getIndexes()` appears reassuring until its partial predicate is compared with the application query. Replacing that index with the complete unique `{user_id: 1}` index restores the access path. `mitigate.sh` does this using only cluster state and standard application defaults. `recover.sh` additionally removes imported historical rows and reverses the storage migration, copying current live timelines before removing the PVC; it restores the saved original Deployment specification.

Validation results are recorded in `validation.jsonl`. The scripts are intended to be run with `NAMESPACE` and optional `ARTIFACT_DIR`; they do not rely on original manifests. Recovery state is saved only in the artifact directory and is not used by mitigation.

The initial incident violated two SLO checks 87 seconds apart, including a window with all 11 rounds violating. Replacing the index returned throughput to approximately 102 requests/second and yielded an entirely healthy 120-second window. Recovery also yielded an entirely healthy window; its second invocation exited successfully and the Deployment specification compared exactly equal to the original. A clean replay and two repeated final-script invocations exited 0, with every application pod Running and Ready. A subsequent continuous 30-minute observation is recorded in `persistence-summary.json`.

The deployment also has pre-existing compose-service OTLP exporter failures naming an unavailable collector. They are unrelated to the timeline access path, were not introduced or modified, and can distract an investigation that follows the first dependency error instead of comparing latency and database work.
