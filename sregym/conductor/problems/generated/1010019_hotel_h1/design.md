A supplier retention/compaction rollout strips address enrichment from retired revisions but keeps those revisions in the same live MongoDB collection. The legacy profile reader has no revision or lifecycle predicate. For five popular IDs, the retained tombstone precedes the current revision in the existing nonunique id index, and the reader returns the tombstone. The application caches that successful but incomplete profile indefinitely. Frontend GeoJSON serialization dereferences the absent address and net/http recovers the panic.

This evolves the earlier retention incident without its conspicuous companion, policy ConfigMap, archive collection, TTL index, or missing records. All 80 current hotel profiles remain intact, including their original ObjectIds. The collection holds 85 documents. A current-profile inspection and a catalog count can look healthy; restoring current records by ObjectId is ineffective because they already exist. Cache flushing and service restarts repopulate the retired revision. There is no reconciliation process to find or stop, and the persisted duplicate revisions have no expiration.

The realistic incident class is a supplier soft-delete/retention migration deployed against a reader that still assumes business-key uniqueness. The existing id_1 index is nonunique. Injection explicitly inserts each retired revision before its active counterpart and verifies the unqualified lookup, so it does not depend on TTL timing or a startup race.

An expert identifies failing hotel IDs from requests/traces, compares cached profile values with all MongoDB rows for those IDs, checks the lookup/index contract, and removes retired duplicates while retaining the complete current revisions. Clearing the cache is also required. The mitigation only needs cluster state. Cleanup uses a snapshot keyed to the database Deployment UID, restoring exact original documents and ObjectIds. No application Deployment, index, or other resource is changed by the scripts; no helper pods are created.

Validation: baseline and restored-state windows each had 4/4 healthy rounds and zero errors. Injection, mitigation, and recovery were each executed twice consecutively with successful exits. Restarting profile and flushing its cache during the incident did not repair the SLO. Two initial violation checks more than 60 seconds apart each had 4/4 violating rounds and a frontend log surge. Mitigation yielded 4/4 healthy rounds with zero errors and p99 54–109 ms. Recovery restored document values and ObjectIds exactly and again yielded 4/4 healthy rounds, p99 56–93 ms. Final replay was executed twice; two checks more than 60 seconds apart each had 4/4 violating rounds, approximately 13.6–15.4% errors, p99 12–15 seconds, and 3,932–4,029 frontend error-like lines per two minutes. All pods remained Running and Ready. The fault is persisted in MongoDB and has no timer or natural healing mechanism. Fixer difficulty remains a hypothesis until independent agents run.
