The incident mirrors a supplier synchronization that imports a global hotel recommendation feed into a regional application's existing catalog. The new records use the same fields, numerical hotel IDs, and ordinary BSON identifiers as the original records. Their coordinates and scores ensure they do not replace the intended local recommendation winners. No deployment configuration, service routing, observability component, or helper resource is added.

The recommender's loadRecommendations function copies the complete collection into an in-memory map. GetRecommendations performs two full scans, with two geographic distance calculations per hotel for distance requests. Importing 4.8 million additional hotel records overwhelms the unchanged one-core scoring budget at production request volume. This is a computation capacity incident, not a database query or RPC response-size incident. Database indexes remain intact. Light-load connectivity checks succeed and pods remain Ready.

An expert would correlate frontend recommendation spans with recommendation CPU, then inspect GetRecommendations and compare the loaded recommendation population with the profile population. Merely pruning the database does not update the map. The reference mitigation computes the eligible ID set from live profile data, prunes unbookable recommendations, and recreates the recommender. Its existing Consul client does not automatically retire registrations on termination, so the scripts deregister the old instances as part of the restart.

inject.sh is repeatable and resumes partially completed imports by checking each batch against existing IDs before inserting missing records. It preserves the original recommendation ID set locally for exact catalog cleanup. mitigate.sh uses only live cluster data; recover.sh uses the saved original ID set. Original records are never changed. There are no timer-based triggers, controllers, new collections, or workloads. Restarts and deployment rollbacks preserve the oversized durable catalog.

The scoring loops do not check cancellation, so work continues after clients time out. This compounds saturation and makes a database cleanup insufficient until the loaded snapshot and pending work are retired.

Validation at the final catalog size: two consecutive checks at least 60 seconds apart reported violated SLOs, with roughly 4–6 requests/second and a recommendation CPU surge from about 0.07 to 1 core. A repeated injection retained exactly 4,800,080 records and the failure persisted across the restart. Two mitigation runs removed 4,800,000 and then zero records; all four subsequent measurement rounds were healthy. Two cleanup runs also succeeded, followed by four healthy rounds at roughly 98 requests/second with zero errors and p99 around 51–63 ms. The incident is replayed once more for submission.

The final replay completed successfully. Two final checks more than 60 seconds apart both had all four rounds violated. The second reported 4.6–5.5 requests/second and 100% timeouts, with the ContainerCPUThrottling alert firing and recommendation CPU at 1 core versus the 0.068-core baseline. The recommendation pod remained Running and Ready. The incident is left active.
