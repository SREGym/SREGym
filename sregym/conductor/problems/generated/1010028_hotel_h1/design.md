The previous incident was solved by comparing recommendation IDs with profile IDs, shrinking the recommendation catalog, and restarting its in-memory snapshot. This evolution changes that diagnostic path: a supplier onboarding batch populates BOTH existing catalogs. The imported hotels have ordinary scalar fields, short numerical identifiers, and the same existing indexes. They are not yet bookable: only the regional hotels have positive room inventory in reservation-db.number.

The batch supplies 24,000 hotels with the regional price floor (120) and rating ceiling (232) as default scores. The scoring code returns EVERY hotel tied at an extremum, without a top-K bound. Rating and price requests therefore produce 24,000-plus IDs even though the recommender itself has relatively modest CPU demand. The frontend forwards those IDs to profile. GetProfiles performs a cache multi-get, launches one goroutine per cache miss, reads MongoDB, and encodes all profiles. Cache pressure, enormous enrichment batches, and expired work overwhelm shared profile capacity and also affect ordinary hotel searches. Cache timeout panics can restart profile and produce stale discovery registrations, a real secondary consequence of the overload.

This mirrors onboarding a supplier directory before booking activation, combined with replacing unavailable ranking values by valid-looking best-case defaults. A valid profile is not proof of bookable inventory. The compact recommendation ID message hides the much larger enrichment cost; enlarging receive limits would not fix the underlying cardinality contract.

An expert should compare distance versus rating/price requests, correlate recommendation and profile trace spans and CPU, inspect the exact-tie scoring loops, group recommendation values by price/rate, and join hotel IDs against positive reservation room inventory. Catalog indexes and document shape remain normal. Profile membership admits every imported row, so the earlier mitigation is ineffective. Fixing eligibility requires the independent reservation inventory or an explicit top-K application fix. The reference fix removes unbookable rows from both catalogs, then retires loaded snapshots and queued work, clears cached enrichment, and cleans old Consul registrations.

inject.sh upserts stable numerical IDs in both existing collections and waits for the new recommender's actual discovery registration rather than using a timer. It changes no Deployment, ConfigMap, network policy, image, or observability resource. Replaying or restarting reuses durable catalog state. recover.sh retains the saved original key sets and removes only imported records; original documents and indexes are untouched. mitigate.sh derives its key set exclusively from live positive room inventory. reload.sh is a shared script shipped with the artifact; it creates no helper workload.

Validation: repeated injection retained exactly 24,080 records in each existing catalog. Restarting recommendation/profile and flushing the profile cache left all four rounds violated. Both mitigation runs succeeded, with the second deleting zero rows. Cleanup was also repeated successfully. The final versions of mitigation and recovery each produced four healthy rounds with zero errors at approximately 96–99 requests/second and p99 below 81 ms. The last replay produced two consecutive violated verdicts more than 60 seconds apart, each with all four rounds violated. Frontend/profile error log surges and recommendation/database CPU surges satisfy observability. Profile reached approximately one CPU core and 2.5 GiB while recommendation remained Running and Ready. No timeout, controller, or automatic retention will remove the durable supplier records. The incident is left active.
