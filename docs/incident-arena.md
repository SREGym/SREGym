# Incident Arena problems

SREGym includes all 20 incidents of [Incident Arena](https://github.com/abundant-ai/incident-arena)
together with the three systems they run on. The incidents are generated by
[abundant-ai/sre-world](https://github.com/abundant-ai/sre-world). Each one starts a live system
under cyclical load and fails it with one or more independent causes, many of which only show up
at traffic peaks or behind another fault.

```bash
# all 20
uv run main.py --suite incident-arena --agent stratus --model gpt-5
# one
uv run main.py --problem incident_arena_slack_maintenance_collision --agent stratus --model gpt-5
```

## Applications

| App (namespace) | System under test | Load generator |
|---|---|---|
| Frappe (`frappe`) | Frappe v16 site (gunicorn/nginx Desk API), MariaDB 10.6, a Redis cache, a Redis queue (RQ), and one supervised long-queue worker | Desk CRUD, prepared reports, and RQ enqueue/complete through a 32-session pool |
| Saleor (`saleor`) | Saleor 3.21 GraphQL API (uvicorn) and Celery worker over PostgreSQL 16, Valkey and RabbitMQ | storefront browsing and checkouts on a 3-shape peak/trough cycle |
| Slack Spine (`slack-spine`) | A polyglot Slack clone: 9 TypeScript roles, Go real-time and connection tier, Python async workers over Redpanda, PostgreSQL 16, Redis, MinIO | seeded open-loop sends, reads, sessions and WebSocket delivery |

Each app is a Helm chart in [SREGym-applications](https://github.com/SREGym/SREGym-applications)
(`frappe/`, `saleor/`, `slack-spine/`; each README lists provenance and the SREGym edits), deployed
with SREGym's values overlay (`sregym/service/apps/incident_arena/values/<app>.yaml`). Incident Arena's own harness is
switched off:

* SREGym's Prometheus/Loki/MCP stack replaces the in-chart observability. `sregym/observer/prometheus`
  scrapes the same exporters and application metrics.
* The chart's load generator keeps running with the task's own traffic profile, looped for the whole
  run. It is labelled `app: load-generator`, so agents never see it. The load generator sends nothing
  until its episode is started (`POST /grader/episode-start` with the in-pod grader token), which
  Incident Arena's harness did once the system was healthy. SREGym makes that call after the chart's
  seed Jobs complete, and restarts the load generator if its episode fails before sending traffic.
* An `ops-toolbox` pod replaces Incident Arena's confined operator shell. It has the same repair CLIs
  and privileged database DSN, so the operational repair paths the tasks were designed around
  (`psql`/`mysql`, `restart-svc.sh`, `reconfigure-infra.sh`) are still available. Agents can also use
  kubectl as usual.
* Images are the digests Incident Arena pinned, from `ghcr.io/abundant-ai/sre-world` (linux/amd64 only).

### What the agent sees

The application description includes the original incident ticket (for example "Message writes
slow down during each recurring peak…") and the app's ground rules. The ground rules state the
constraints that Incident Arena enforced by withholding Kubernetes access: repair in place through
the system's operational surfaces, keep the deployed release, and do not restart, rescale,
broaden grants or capacity, flush data, disable safeguards or suppress traffic to mask a fault.

### Fault injection

Problems deploy a healthy system and inject at a controlled time, mirroring how each task committed
its fault:

* **MariaDB:** `REVOKE`/`SET GLOBAL` as root.
* **Redis queue flags:** written into the Bitnami start script and the broker restarted, so the
  flags persist like the chart value did. frappe-admin repairs the same script.
* **Slack pools:** written into the `app-config` ConfigMap and applied live through
  `/admin/config` + `/admin/reload`.
* **Runtime events:** `PUT /admin/event`. The latent hold dose (`STORE_HOLD_MS`/`ACL_HOLD_MS`) is
  deploy-time env, as in Incident Arena.
* **Maintenance schedule:** `PUT /v1/maintenance`, which stores it durably in PostgreSQL.
* **Sequencer mode:** env on the Deployment.
* **Saleor:** `ALTER ROLE ... IN DATABASE`.
* **Image faults (018, 019):** the faulty build is deployed as the release, so injection waits for
  the leaked lock. Incident Arena forbids rolling back that build.
* **Task 005:** its accepted backlog (two Prepared Reports, one with its RQ job stranded, and four
  emails delivered to an in-cluster Mailpit sink) is seeded while the queue cannot dequeue.

### Grading

* **Diagnosis:** SREGym's LLM-as-a-judge, against every (service, component) finding in the task's
  answer key plus the concrete injected mutation.
* **Mitigation:** `IncidentArenaMitigationOracle` reproduces Incident Arena's two gates on the live
  cluster:
  1. **Safe repair (white-box).** The injected cause is gone. The change stayed in scope:
     * Frappe: no unrelated grants or globals, no worker scaling, cache untouched.
     * Slack: only the owned config keys, pools within the 20/10 budget, release image unchanged,
       PostgreSQL settings unchanged except the allowed ones.
     * Saleor: no other timeout scopes, no restarts, capacity unchanged.

     Runtime toggles were not cleared by restarting the role. The repair also survives the
     verifier-owned challenge: a redis-queue broker restart, a svc-message restart, or the
     re-asserted compliance window.
  2. **Outcome.** After the challenges, the oracle soaks for the task's `soak_s`. It then reads the
     load generator's own request ledger and checks error rate, correct goodput, per-driver lanes
     and, where Incident Arena gates it, the p90/p99 latency per peak/trough. It uses the task's
     bands with Incident Arena's 20% tolerance. The latency bands are absolute milliseconds
     calibrated on Incident Arena's hardware, so each one is raised to twice the healthy latency
     this cluster showed in the 180 s before injection when that is higher. On hardware like
     Incident Arena's the task's own bands apply unchanged. Tasks 018 and 019 keep the absolute
     bands, because their faulty release runs from deploy.

  Failures carry SREGym's failure classes:
  * Fault still present, unsafe or non-durable repairs, and restart-masking are `agent_error`.
  * Unhealthy outcomes are `ambiguous`.

## Requirements and caveats

* Images are amd64-only.
* Incident Arena sized each task for 8 vCPU / 16 GB on its own. Slack Spine runs about 40 pods
  (about 4 vCPU of requests) next to SREGym's stack, so use the recommended SREGym-Lite machine or larger.
* The first Frappe install runs `bench new-site` and can take 15–30 minutes. The app waits up to 45.
* The charts use ReadWriteOnce volumes shared by several pods of one app. That works with
  SREGym's default `openebs-hostpath` (local PVs pin consumers to one node) and on kind.
* Every problem passes `tests/integration/validate_problem.py` end to end (deploy, inject, oracle
  fails, recover, oracle passes) on a 4-node kind cluster on a 16-thread 2.0 GHz Xeon D-1548, and is
  covered offline by unit tests and `helm template` (`tests/incident_arena`). The Saleor problem also
  passes SREGym's GitHub Actions problem validation (kind on a 4 vCPU runner).
* SREGym sizes three components above the charts' defaults, because its load runs for the whole
  run and some hosts are slower than Incident Arena's: Saleor's API gets 4 uvicorn workers and 4 CPU
  (checkouts queued past the load generator's timeout at 2 CPU on a 2.0 GHz host), Slack's
  in-memory search-engine gets 2 CPU (the async search lane fell behind as its corpus grew), and
  Frappe runs two long-queue workers (one drained Prepared Report jobs slower than they arrived).
  Problems still forbid agents from changing these.
* Incident Arena's binary graded report (the closed service/component vocabulary) is replaced by
  SREGym's free-text diagnosis stage. The incident report was advisory in most Incident Arena tasks anyway.
